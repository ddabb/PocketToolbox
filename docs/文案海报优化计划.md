## 1. 背景与目标

文案海报（1.4.3 交付）已上线 18 个模板、3 种比例（1:1 / 3:4 / 9:16）、5 套配色、5 字体、注音开关。
功能闭环，但**出图品质存在一批可验证的硬伤**——用户在模板选择器里一眼就能看出「这个没做好」，
直接压制分享意愿（这正是工具的核心场景）。

本计划**不新增模板、不改交互、不加功能**，只做两件事：

| 目标 | 说明 |
|---|---|
| ① 排版引擎化 | 把散在 18 个 Builder 里的手写排版收敛为一套可复用的排版内核，解决溢出/错位/留白等共性缺陷 |
| ② 模板效果精修 | 逐模板修构图、对齐、遮挡、留白，让 18 张卡片达到「可直接分享」的完成度 |

**明确不做**：新增模板 / 新增比例 / AI 文案 / 用户自建模板 / 素材库 / 水印自定义 / 埋点。

### 与 1.4.5 PDF 工具的排期关系

本计划并入 1.4.5，但**代码改动与 PDF 工具错开**，避免同文件交叉冲突：

| 顺序 | 阶段 | 说明 |
|---|---|---|
| 1 | PDF 工具 Phase 0（已完成 spike） | `pages/PdfSpikePage.ets`，与本计划无文件交集 |
| 2 | PDF 工具 Phase 1-4 | 新增 `PdfComposer/PdfSplitter` + PDF 工具页 |
| 3 | **本计划 Phase A-C** | 改动 `CopyPosterPreview.ets` 等创作侧文件 |
| 4 | 两项统一回归 + 提交 | 同一版本发布 |

## 2. 根因分析：问题不只是「某几个模板不好看」

翻 18 个模板的渲染代码（`components/cover/CopyPosterPreview.ets`，2841 行 / 约 30 个 `@Builder`）
和真机截图后，缺陷可归为 4 类根因。**这是本计划的核心判断——如果只逐个改模板，问题会反复出现。**

### 根因 A：竖版（3:4 / 9:16）与方图共用一套绝对坐标

绝大多数模板用 `.position({ x: this.f(40), y: this.f(40) })` 定位装饰元素，
`f(px) = previewWidth * px / 900` 只按**宽度**换算，高度用 `h()` 另行换算。
装饰件随宽度缩放，但内容区的纵向排布靠 `justifyContent: Center` 居中 —— 一换竖版，
上下留白被拉大，构图比例立刻失衡。

**实证**（截图 `文案海报_效果图_T5_LCD像素屏_文字编辑.jpeg`）：
切到「竖图 3:4」后，T5 预览**塌成一条约 80px 高的黑色横条**，
装饰与内容全部丢失。这是严重 bug，不是观感问题。

> 注：三种比例宽度都是 900 设计稿宽，所以换比例**不改变可用宽度**，只改变可用高度与行数上限。
> 因此内核的输入应是「可用宽度（模板 padding 决定）+ 行数预算（比例决定）」，而非只按字数分档。

### 根因 B：主文案分档是硬编码阶梯，与实际容器宽度无关

`bodyFont()` 按字数分 5 档返回固定 px：

```typescript
// CopyPosterPreview.ets:62-87
n <= 8  -> basePx
n <= 16 -> basePx * 0.8
n <= 32 -> basePx * 0.62
n <= 60 -> basePx * 0.48
else    -> basePx * 0.38
```

问题有三：
1. **不感知容器宽度**。同样 20 字，在 `padding: 70` 的 T1 和 `padding: 24` 的 T10 里可用宽度差 90px，字号却完全相同 —— T1 恰好合适，T10 就会顶格或折行难看。
2. **不感知可用高度/行数预算**。9:16 长图行数上限 12 行，却与方图用同一字号档，长文案在长图下显得字小、气势弱。
3. **档间跳变**。字数 32→33 时字号从 0.62 骤降到 0.48，用户边打字边看到字号突变。

### 根因 C：`maxLines` + `Ellipsis` 静默吞字

`BodyBlock()` 用 `.maxLines(this.maxBodyLines(big))` + `textOverflow: Ellipsis`。
超过上限直接截断加省略号，**用户完全不知道自己写的内容被砍掉了**，导出的图少了一句话。
`maxBodyLines` 方图给 8 行、竖图 12 行，但字号分档和行数上限互不联动，两者都撞顶时静默截断。

### 根因 D：slot 位置由各模板自行硬编码，图文关系无约束

`tag`（标签）/ `body`（主文案）/ `sign`（署名）三个槽位，每个模板自己决定字号、位置、装饰关系。
后果是同类问题反复出现：

| 症状 | 实例（截图证据） |
|---|---|
| 标签与正文串行撞一起 | T5 LCD 屏：`hi 朋友` 挤在 `欢迎来访公众号「随身工具宝」` 左侧同一行 |
| 正文压住装饰件 | T13 黑胶唱片：曲目文字压唱片边缘；正文在唱片下方但间距过窄 |
| 倾斜件留死角 | T9 复古车票：票面 `rotate(-1.5)` 后四角露黑边 |
| 竖版大片空 | T1 暖调标签卡竖版：底部约 40% 为空白 |
| 正文折行不美观 | T11 复古报纸：`「随身工具宝」` 断在引号内 |

## 3. 优化项清单

分三个优先级。**P0 是 bug 与明显缺陷，P1 是完成度，P2 是加分项。**

### P0-1 修复竖版塌陷 bug（根因 A）

| 项 | 内容 |
|---|---|
| 现象 | T5 等斜拍模板切竖版后预览塌成横条 |
| 方案 | 抽出 `posY(py)`（按画布高换算纵坐标）与 `posX(px)`（按宽换算横坐标）两个方法，替换所有 `.position({x,y})` 硬编码；斜拍模板的画板尺寸按 `h()` 而非 `f()` 取基准 |
| 验收 | 18 模板 × 3 比例 = 54 组合，预览区均完整出图，无塌陷/截断/溢出 |
| 风险 | 触及全部模板的定位代码，需逐模板回归（正好与 P0-2 同批做） |

### P0-2 排版内核：按容器宽度算字号（根因 B）

| 项 | 内容 |
|---|---|
| 方案 | 新增 `core/cover/PosterTypeset.ets`，输入「容器可用宽度（设计稿 px）+ 可用行数 + 文案 + 基准字号」，输出「实际字号 + 实际行数 + 是否截断」 |
| 算法 | 先按基准字号估算行数，超出则按 `min(基准 × 衰减, 可用宽/最长行宽)` 连续收缩；**取消 5 档硬编码阶梯**，消除档间跳变；中文字宽按 1.0em 估算，混排英文/数字按 0.55em |
| 兼容（关键） | 保留 `bodyFont()` 签名并新增**可选参数** `availWidthPx`：传入该参数的模板享受内核适配，未传时行为与现在完全一致。这样 18 个 Builder 调用点可分批迁移，任一时刻工程都可编译可运行，回归风险可控 |
| 验收 | 同一文案在 T1/T10/T13 三种容器宽度下均无顶格、无折行错位；字数逐字递增时字号平滑无跳变 |

### P0-3 长文案可见截断提示（根因 C）

| 项 | 内容 |
|---|---|
| 方案 | `BodyBlock` 在超出 `maxLines` 时，于文案下方显示「已省略 N 字」小字提示（编辑区同步显示），并把实际可容纳字数回传给编辑页做字数计数 |
| 验收 | 输入超长文案时明确知道被截断，不静默丢字；导出图与提示字数一致 |
| 备注 | 由 P0-2 内核直接提供「是否截断 + 截断字数」，本项实现成本因此很低 |

### P1-4 逐模板构图精修（根因 D）

按截图证据，每个模板的具体修法：

| 模板 | 问题 | 修法 |
|---|---|---|
| **T1** 暖调标签卡 | 竖版底部大片空白；标签/正文/署名三件纵向间距随比例失衡 | 改用 `justifyContent` 权重分配而非固定 `space`，竖版自动拉开 |
| **T4** 大字冲击 | 长文案降级后气势明显减弱 | `big` 分档的降级路径改为连续缩放，保住大字观感 |
| **T5** LCD 像素屏 | `hi 朋友` 与正文串行相撞；斜拍件竖版塌陷 | 标签独立成行（示例图 `pinyin` 位本就独立）；P0-1 一并修斜拍 |
| **T7** 霓虹灯招牌 | 灯管边框在短文案时显得空旷 | 边框光晕随内容尺寸自适应；**作为 P1-5 分层的样板模板** |
| **T8** 掌机游戏机 | 正文框偏小，长文案挤压；血量/比分装饰与内容关系弱 | 对话框宽度按文案长度自适应 |
| **T9** 复古车票 | `rotate(-1.5)` 后四角露黑 | 票面放大到覆盖旋转后的包围盒 |
| **T10** 翻牌显示屏 | 底板固定 `f(790)` 宽，长文案换行后行数多时超出底板 | 底板高度随行数增长；`flapRows()` 行宽按比例重算 |
| **T11** 复古报纸 | 引号内断行（`「随身工具宝」` 被拆）；报纸线块为静态 | 短词优先换行（避免引号/标点行首）；线块宽度随正文长度变化 |
| **T12** 聊天气泡 | 气泡宽度固定，长文案溢出风险 | 气泡宽度按字数分级 |
| **T13** 黑胶唱片 | 曲目文字压唱片边缘 | 唱片与曲目区间距重排，缩略图 `A1/B1` 段下移 |
| **T14** 电影字幕卡 | 内容整体偏上，底部空 | 垂直居中权重调整 |
| **T16-T18** | 无基线效果图，构图未经验证 | 随 P1-5 分层统一修正；走查时补截图留档（**不单独安排基线补图阶段**） |

### P1-5 装饰层与内容层解耦（根因 D 治本，**已裁定必做**）

| 项 | 内容 |
|---|---|
| 方案 | 把「装饰层（背景/边框/光晕/纹理）」与「内容层（三个 slot）」拆成两个独立 Stack；装饰层跟随 `h()`，内容层用 P0-2 的排版内核居中 |
| 样板 | 先迁 **T7 霓虹灯招牌**（装饰层与内容层边界最清晰），验证可行后再铺开其余模板 |
| 收益 | 新增模板只需写装饰层 + 声明 slot 权重，不必再手写全套坐标；根治 P0-1 / P1-4 各类塌陷 |
| 验收 | T7 样板 3 比例 × 5 配色无回归；其余模板迁移后 54 组合全通 |

### P2-6 T16-T18 缩略图与细节核查（已裁定必做，含结论修正）

> **结论修正（2026-10-12 代码核查）**：本项最初判断为「缩略图缺失、列表滑到底会空白」，
> 经核查代码该判断**不成立**，已修正。
>
> 核查依据：
> - `CopyPosterTemplates.ets` 实有 18 个模板，T16/T17/T18 均在注册表内（`grep` 确认 18 次 `list.push`）；
> - `CopyPosterPreview.ets` 的 layout 派发链含 `solar_term` / `festival_greet` / `red_couplet` 三个分支，
>   对应 `SolarTerm()` / `FestivalGreet()` / `RedCouplet()` 三个 Builder 均已实现；
> - 缩略图**不是独立图片资源**，而是 `TemplateScroller()` 遍历 `CopyPosterTemplates.all()`
>   用同一 `CopyPosterPreview` 组件实时渲染（`previewWidth: 96`、`showWatermark: false`）。
>   因此只要模板在册，缩略图必然出现。
>
> **真正的问题不是「有没有缩略图」，而是这三张在 96px 缩略尺寸下是否可辨识。**
> 实际改动因此变为：

| 项 | 内容 |
|---|---|
| **T16 缩略图可辨识** | `SolarTerm()` 主文案为竖排 + 边框双线 + 四角菱形，96px 下正文极小近乎不可读。缩略图场景改用较粗的节气名表现，正文降级为装饰性笔画感 |
| **T17 缩略图可辨识** | `FestivalGreet()` 由 8 个 `FestStar` 星点 + 3 层同心圆构成，96px 下星点与圆环混成噪点。缩略图场景按 `previewWidth` 阈值跳过细节星点，只保留月亮+圆环主形 |
| **T18 缩略图可辨识** | `RedCouplet()` 红金对联 + 铜钱团花，96px 下金红对比过密。缩略图场景保留主体竖批，团花降透明度 |
| 缩略图与主预览一致 | 缩略图渲染的是**用户当前内容**，长文案时 96px 下更糊。接入 P0-2 内核后字号按 96px 容器重算，短文案仍保持可读 |
| 深色模式走查 | 空文案占位、装饰层在深色下的对比度 |
| 缩略图一致性 | 现有缩略图关水印（`showWatermark=false`），确认为有意设计后保留 |

> 实现方式：给三个 Builder 增加「缩略图模式」判断（复用现有 `showWatermark` 同类做法，
> 新增一个 `@Prop isThumb: boolean = false`，由 `TemplateScroller()` 传入 `true`），
> 在该模式下精简细节层，保证 96px 下主形可辨识。

## 4. 范围外（本期不做）

- 动态图/视频导出；
- T16-T18 单独的基线效果图补拍（随走查顺带留档）。

## 5. 技术方案要点

| 项 | 内容 |

### 10.2 根因 E：内核路径漏 f() 缩放（本次核心修复）

```
f(px) = previewWidth × px / 900        // 设计稿 px → 预览 vp，全文件定位/字号统一换算
旧阶梯路径：s = this.f(basePx) → fontSize(s)   ✓ 正确
内核路径（修复前）：fontSize(layout.fontPx)    ✗ 设计稿数值直接当 fp 用
```

- 预览宽 234vp 时字号被放大 900/234 ≈ **3.8 倍**；走查实证 T1 满文案 body 高 776px（正确值约 236px），每行仅容纳内核估算 1/3.8 的字数。
- 导出路径按设计稿 900 直接绘制，本来就是正确的——**只有预览渲染漏了换算**，故此前导出图正常而预览失真。
- 修复（`CopyPosterPreview.ets` bodyFont 内核分支）：

```typescript
let px: number = this.f(layout.fontPx);   // 设计稿 px → 预览 vp，修复 3.8 倍放大
this.layoutCache = layout;                // layoutCache 仍存设计稿 layout，truncatedHint 只读字数，无单位问题
return this.pyEnabled() ? px * PY_SHRINK : px;
```

- 渲染级验证（T1，14 字）：内核 fontPx=66 → f(66)=17.2vp → 51.5 物理/字 × 14 字 = 721px，实测 body 宽 726px，**误差 < 1%**。
