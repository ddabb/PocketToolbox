# 数独识别回归分析 — P0~P3 优化后准确率归零

> 2026-08-07 | P0-1~P3-1 全部实施后，拍照/截屏测试图片识别准确率降至 0%，表现为大量莫须有数字填充空格。本文档定位根因并记录修复状态。

---

## 一、症状

| 现象 | 说明 |
|------|------|
| 空格被填充 | 原本为空的格子被识别为 1~9 数字 |
| 数字识别错误 | 已有数字也可能被替换为错误数字 |
| 截屏 & 拍照均受影响 | 合成变体/截屏/照片全面退化 |
| 像素路径和 VisionKit 路径均受影响 | 两条路径都产生虚假数字 |

---

## 二、根因分析

### 根因 #1: `recognizeDigit` 匹配分数对空格签名严重偏高（致命）

**位置**: `SudokuPixel.ets:1752-1839`

签名从 12×8=96 位升级到 28×20=560 位后，`recognizeDigit()` 的匹配分数公式未适配：

```
score = match - (SIG_LEN - match) * 0.5 + f1 * 200
```

- `match` = 签名与模板中相同位的数量（含 0==0 的背景匹配）
- 空格签名：560 位中绝大多数为 0
- 数字模板：560 位中也大量为 0（数字墨迹仅占 30~50%）
- 结果：空格签名与任意数字模板的 `match` ≈ 560×0.6 = 336+
- 得分：`336 - 224×0.5 + ... = 224+`，远超阈值 60

**12×8 时为何没问题**：96 位下空格匹配分 ≈ `60 - 36×0.5 = 42`，低于阈值 60（旧阈值），且墨点下限 25/96=26% 很难达到。

**560 位下的问题**：
- 墨点下限 25/560 = 4.5%：空格中微小噪声/网格线残影即可达到
- 分数阈值 60 过低：空格匹配分轻松超过 60
- 结论：**空格必然被识别为某个数字**

### 根因 #2: `cellSigFromGray` 墨点范围阈值未适配 560 位签名

**位置**: `SudokuPixel.ets:1466,1494,1522,1585,1659,1719`

| 阈值 | 当前值 | 560位下含义 | 合理值(560位) |
|------|--------|------------|-------------|
| 最低墨点 `inkCount < 25` | 25 | 4.5% | ~140 (25%) |
| 最高墨点 `inkCount > 420` | 420 | 75% | ~420 (75%, 尚可) |
| 最低墨迹占比 `ink < area * 0.02` | 2% | 尚可 | 3~5% |

25 的墨点下限在 96 位时是 26%，在 560 位时仅 4.5%。空格中残留网格线、Sauvola 噪声等轻松超过此阈值。

### 根因 #3: `fixAndFillGrid` 对空格进行强制填充

**位置**: `SudokuOCR.ets:227-382`

合并后的 `fixAndFillGrid()` 对所有 `grid[i] === 0` 的格子尝试像素识别+VisionKit重识：
- 数独题目中空格是正常状态（待求解位置）
- 该函数把空格当成"缺失"来填充
- 结合根因 #1，像素识别必然给空格分配一个数字

### 根因 #4: `cropSubPixelMap` 目标尺寸错误（已修复）

**位置**: `SudokuOCR.ets:139-170`

原始实现创建目标 PixelMap 时使用了 `cropW * upscale` 尺寸，然后写入 `cropW × cropH` 数据，再 `scaleSync(upscale)`，导致 9× 放大和数据错位。

已修复为：先创建 `cropW × cropH` 尺寸 → 写入数据 → 再 `scaleSync`。

### 根因 #5: `findConflictCells` 把题目已知数字的合法重复当作冲突

**位置**: `SudokuOCR.ets:104-138`

`findConflictCells` 检测行/列/宫格中的数字重复，但数独题目本身就是残缺的——已知数字之间本就不冲突，问题在于 VisionKit 可能将多个数字识别为同一数字导致真实冲突。此函数的语义没问题，但被 `fixAndFillGrid` 滥用：它对所有冲突格重新识别，而非仅针对低置信格。

## 三、修复方案

### Fix #1: 空格签名检测 — 墨点下限和分数阈值适配

**修改文件**: `SudokuPixel.ets`

1. **墨点下限**: `inkCount < 25` → `inkCount < SIG_LEN * 0.25`（560×0.25=140）
2. **墨点上限**: `inkCount > 420` → `inkCount > SIG_LEN * 0.75`（560×0.75=420，不变）
3. **Sauvola 墨点范围**: 同步调整 `sauvInk >= 25` → `sauvInk >= SIG_LEN * 0.25`
4. **recognizeDigit 阈值**: `bestScore >= 60` → `bestScore >= SIG_LEN * 0.65`（560×0.65=364）
5. **inkCount 检查**: `inkCount < 25` → `inkCount < SIG_LEN * 0.25`

核心思路：阈值必须基于签名长度的百分比，而非绝对值。

### Fix #2: 停止对空格的强制填充

**修改文件**: `SudokuOCR.ets`

1. `fixAndFillGrid` 中移除 `emptyIndices` 处理逻辑
2. 仅保留冲突格的修正逻辑
3. 空格 = 0 是合法结果，不应强制填充

### Fix #3: 冲突修正增加置信度门控

**修改文件**: `SudokuOCR.ets`

1. 仅对 `confidence < 0.5` 的冲突格尝试重识
2. 高置信格的冲突更可能是题目本身特征，不应覆盖
