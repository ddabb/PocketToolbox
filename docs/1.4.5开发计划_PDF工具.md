# 1.4.5 开发计划：PDF 工具（生成与拆分）

> 状态：已批准（2026-10-12 用户决策，见 §8，全部裁定）
> 前置：1.4.4 第二批已收官并推送 origin（`bafcf69..1271f2b`），本计划为 1.4.5 主题。

## 1. 背景与目标

1.4.4 完成留存体系（成就/复习/签到）与创作工具历史化后，工具箱缺失高频文档场景：**PDF**。1.4.5 引入 PDF 工具双能力：

1. **图片合成 PDF**：多选相册图片 → 排序/配置 → 导出一份 PDF（扫描件、长图整理场景）；
2. **PDF 拆分为图片**：选取 PDF → 逐页渲染导出 JPEG/PNG → 保存相册（课件截图、单页提取场景）。

目标版本：versionName **1.4.5**、versionCode **1000025**、build 14（用户已确认，2026-10-12）。

## 3. 交互设计
1. 入口：工具页新增「PDF 工具」卡（单卡），进入后顶部双 Tab「合成 / 拆分」（对齐文案海报 EditorTabs 模式）；
2. 动线遵循「先输入后配置」：合成=先选图后配置页面模式/方向/文件名；拆分=先选文件后配置导出格式/质量；页列表即实时结果锚点；
3. 空态：合成空态=大按钮「选择图片」；拆分空态=大按钮「选择 PDF」；
4. 三语（zh/base/ja）全量文案 parity；深色模式适配；无埋点。

## 4. 技术方案
1. **核心 Kit**：`@kit.PDFKit` 的 `pdfService`，**起始版本 5.0.0(12) < 工程 compatibleSdkVersion 5.1.0(18)，无 API 守卫负担**；
2. **合成**：`new pdfService.PdfDocument()` → `createDocument(w, h)`（pt 单位，A4=595×842pt）→ 逐图 `insertBlankPage(index, w, h)` + `getPage(i).addImageObject(path, x, y, w, h)` → `saveDocument(path)` → `releaseDocument()`；px→pt 按 72/96 换算；
3. **拆分**：`loadDocument(path, password)` → `getPageCount()` → 逐页 `getPagePixelMap(pageIndex, isSync=false)` 得 `image.PixelMap` → image Kit 打包 JPEG/PNG → 复用既有相册保存链路（系统保存对话框）；每页渲染后及时 `release()`；
4. **选源**：图片走 photoAccessHelper.PhotoViewPicker（多选）；PDF 走 DocumentViewPicker select（mimeType 过滤）+ 拷贝沙箱；
5. **输出**：PDF 生成至 `filesDir`，保存走 DocumentViewPicker.save（用户选目录）；分享复用系统分享面板；
6. **约束**：loadDocument 不可重复调用，每次操作 new 文档对象并 releaseDocument；文档不可同时读写，覆盖保存需临时文件过渡。

**关键发现（已修）**：`pdfService.PdfDocument.createDocument(w, h)` 创建后**自带一个初始空白页**（尺寸即传入的 w×h），后续 `insertBlankPage` 的页都在它之后。若不删除，导出 PDF 第 1 页为空白页。修法：所有内容页插入完成后、saveDocument 之前，`doc.deletePage(0, 1)` 删除初始页（spike 内已验证删除后页序正确）。

其余结论：
- px→pt 按 72/96 换算封装有效，A4=595×842pt 与「适应图片」两模式均可正常建页；
- loadDocument/getPagePixelMap 生命周期按 §4.6 约束执行无冲突；
- 社区反馈的「addImageObject 内容空白」当时未复现——**该结论仅对沙箱路径成立**：spike 用沙箱内测试图验证；相册 media URI 直传的路径未覆盖，后在正式页真机复现（见 §10 修复记录）。

Phase 0 达成验收，spike 页已于正式页落地时移除（提交 538847d），验证逻辑迁移至 `core/pdf/PdfComposer.ets` 与 `core/pdf/PdfSplitter.ets`。

### 空白页缺陷与修复（2026-10-13 同日发现、修复并复验）

**现象**：上表首轮验证流程全部走通，但用户在真机相册查看发现：拆分导出的图片是空白的；合成出的 PDF 页面也无内容。即链路「机械成功」、内容全空。

**根因**：`PdfComposer.compose` 把 PhotoViewPicker 返回的相册 URI（`file://media/...`）直接传给 `page.addImageObject()`。pdfService 原生层解析不了媒体库 URI → **静默不绘制、不报错** → 生成全空白页的 PDF；拆分链路忠实渲染了这些空白页，导出图自然全白。Phase 0 spike 用的是沙箱内生成的测试图（从未走 media URI 路径），故 §9 未暴露。官方知识库案例（PhotoViewPicker 选图 + PDFKit 合成）的流程正是：**先 `fs.openSync(uri)` 得 fd、`copyFileSync` 拷贝到应用沙箱，再把沙箱路径传给 `addImageObject`**。

**修复**（`core/pdf/PdfComposer.ets`）：
- compose 循环内：每张图先 `openSync(uri)` → fd → `copyFileSync` 到 `filesDir/pdftool_tmp/img_N.<ext>`，`addImageObject` 改传沙箱路径；拷贝失败报 `copy` 短码走既有失败提示；
- 临时目录在 compose 开始前清理历史残留、`finally` 中整目录删除（含失败路径，不残留）；
- 顺带加固：`insertBlankPage` 索引由 `i` 改为 `inserted`——跳过某图时内容页仍保持连续，`deletePage(inserted,1)` 恒删初始空页（与文件头真机实证一致）。

**修复后真机复验**（Mate 60 Pro，构建重装后）：

| 项 | 结果 |
|---|---|
| 合成 | ✅ 选 2 图 → 生成 PDF **265KB**（空白 PDF 仅数 KB，量级差即证据）→ 结果文字「已生成 2 页」 |
| 保存 | ✅ DocumentViewPicker.save 返回 errorcode 0，无 `[PdfTool]` 错误日志（成功 toast 1.5s 未被截图捕获，以日志判定） |
| 拆分 | ✅ 选该 265KB PDF → 缩略图**显示照片内容非全白** → 导出 → 相册授权 → 「已导出 2 张图片到相册」toast 直接观察到 |

结论：空白图缺陷修复闭环，合成→拆分全链路内容正确。此前首轮验证留存在真机的空白 PDF/空白导出图为缺陷期产物，可手动删除。
