### 1.3 目标与非目标

**目标**：(1) 生字卡多音字标注强化——对抗性多音字文本（干一行爱一行/行行行则行行行类）从「逐字 8+ 次点选」降到「1 次批量 + 局部改回」，修正功能可发现；(2) 1.4.9 裁剪项 A4/A5 收口；(3) 1.4.9 真机统一回归与 AGC 发版落地（M0）。

**非目标**：不追求对抗性文本自动标注全对（语义歧义无词典可依，§2 实证）；不动 1.4.8 已验收的拼音选项式/标点跟随/逐段注音语义；不加新模板 T22+；不动四独立应用（各自按立项文档推进，本期仅复用产出反哺其复用资产——字帖生成器已列名复用 CharPinyinEditor 拼音修正交互）。

## 2. 摸底：多音字标注链路与实测（2026-10-25，立项依据）

### 2.1 现状链路

- 自动注音：`CoverContentUtil.autoPinyin` 逐段注音（1.4.8 标点修复改造：按连续汉字段分段调 pinyin-pro，段内多音字上下文保留，标点/拉丁/emoji 不进入参）→ `pinyinRun` → pinyin-pro 3.26.0（root oh-package.json5）。
- 手动修正：`CharPinyinEditor`（components/cover/，1.4.8 M3）逐字 chips，`correctable(idx)` = `pinyinCandidates(ch)` 候选数 ≥2 才可点选；候选选项式修正 + 每字「恢复自动」；修正持久化且导出图一致。首图页（CoverMakerPage）另有一套内嵌拼音修正，同用 `CoverContentUtil.replaceSyllable/pinyinCandidates`。
- 生字卡无 TTS 朗读，标注仅用于预览格与导出图拼音行（rowPinyinSlots）。

### 2.2 实测（node + oh_modules/pinyin-pro 3.26.0，2026-10-25）

| 输入 | 输出 | 判定 |
| --- | --- | --- |
| 干一行，爱一行，行行行则行行行 | gàn yì háng / ài yì háng / **xíng×6** | 前两段词典命中正确；「行行行则行行行」全误（语义应为 háng háng xíng zé háng háng xíng 类混合读） |
| 行行出状元 | háng háng chū zhuàng yuan | 成语词典命中，正确 |
| 干一行行一行，一行行行行行 | gàn yì háng **xíng** yì háng, ... | 同句同字混合输出（一处 háng 一处 xíng），批量盲改必误伤某侧 |
| 海水朝朝朝朝朝朝朝落 | zhāo×6 + 错位 cháo | 名联对抗性文本，分词失效 |
| 银行/自行车/行李/行业/重庆/长大/人参/重复/参加 等 15 词组 | 全部正确 | 常规词组词典 15/15 覆盖 |
| pinyin('行', {multiple:true}) | xíng/háng/hàng/héng | 手动候选齐全，正确读音可达 |
| pinyin(…, {restoreTone:true}) | 输出不变（yì） | restoreTone 传参无效，变调还原无现成开关 |
| 包导出 | addDict/customPinyin/polyphonic/segment 等存在 | 自定义词典 API 可用（3.26.0） |

### 2.3 失败模式归类与结论

1. **类型① 常规词组/成语**：pinyin-pro 词典已覆盖（15/15 + 行行出状元），**无需词典补丁层**。
2. **类型② 用户自造对抗性文本**（行行行则行行行/干一行行一行）：无词典可依、语义歧义自动不可解；且同句同字混合读音（háng 与 xíng 交错）使「一刀切批量」必产生反向误伤——**正解 = 高效人工修正链路：批量应用 + 逐字改回 + 每字恢复自动**。
3. **类型③ 变调显示**（一→yì、不→bù）：非多音字问题，教学口径问题，实测无现成开关，顺延（§7）。
4. 痛点量化：样例句现状需 6 字 × 2 次点选（chip+候选）= 12 次点选；批量修正后 = 1 次选候选 + 1 次批量应用 + 2 字改回 ≈ 6 次，统一读音重复字场景收益更大（2 次 vs 4+ 次）。
5. 发现性缺口：correctable 与非 correctable 字 chip 无视觉区分，用户不知道「这字能点」。

## 3. 方案设计

### 3.1 P0-A 生字卡多音字标注强化

- **A1 同字批量修正**：`CoverContentUtil` 新增纯函数 `batchReplaceSyllable(chars, pinyinText, ch, syllable)`（同字全部位置替换，返回新 pinyinText，坏参防御对齐 replaceSyllable 风格）；`CharPinyinEditor` 候选行尾追加「应用到全部『行』(N 处)」次级 chip（N=同字出现数，实时计数），点击批量替换；已修正位可再批量覆盖、可逐字「恢复自动」（反向兜底）。批量语义（是否含已修正位）见 §8-1。
- **A2 可修正视觉提示**：correctable 字 chip 加视觉区分（淡色底或下缘点，深色双资源适配），非 correctable 不变；解决「能点不知道」发现性缺口。
- **A3 首图同函数接入**：CoverMakerPage 内嵌拼音修正接入 `batchReplaceSyllable`（同函数零重复实现，§8-3）。
- **A4 语料测试沉淀**：新增 ohosTest 纯逻辑套件（暂名 polyphoneTest，注册进 List.test，13→14 纯逻辑套件）：类型① 正例锚定（15 词组+成语）、类型② 现状锚定（行行行则行行行=xíng×6，防无意识回归）、`batchReplaceSyllable` 纯函数（同字全替换/无同字早退/空串坏参防御/锁定位覆盖语义）。
- **A5 词典缺口预留**：M1 若发现成语/高频词词典缺口（类型① 反例），用 `addDict`/`customPinyin` 补丁；摸底未发现缺口则零改动。

### 10.2 「chips 不渲染」排查结论：视口裁剪假象，非缺陷（重要方法论留档）

M1-A4 E2E 期间出现「chips 在 JS 层构建（hilog itemGenerator 34 次执行）但 dump 无节点、候选区像素缺失」，跨 1.4.9/M1 多版本复现，最终定性为**测试方法问题**：

- **根因**：模拟器 API 24 上输入框聚焦弹 IME 后窗口压缩至 ~1700px，页面 Scroll 视口底缘 y=1522；编辑器恰好整体落在折叠线下，hint 仅 5px 可见（dump bounds 如实反映裁剪后可见区域），chips/候选/批量 chip 全被 clip。`uitest dumpLayout` 对完全裁剪节点不输出 → 误判「未构建/未渲染」。
- **证据链**：dump 树 `Scroll [0,137][1256,1522]` + 编辑器根 Column `[56,1517][1200,1522]`（5px）；`uitest uiInput swipe` 上滑后 chips 立即出现于 dump（y1381）与截图；纯 1.4.9 构建同现 → 与 M1 代码无关。
- **教训**：
  1. dump「节点缺失」先算视口账（窗口挤压/滚动位置/clip 边界），勿直接下「未渲染」结论；
  2. 像素断言须对准 dump 给出的节点可见 bounds，而非按记忆中的布局猜区域（本例 38px「纯白 gap」实为固定底栏白区）；
  3. E2E 步骤中凡断言/点击折叠线下控件，先 swipe 揭示再操作；
  4. 插桩日志证明「JS 构建完成」与「像素可见」是两个命题，中间隔着布局/裁剪层。
- **撤销的无效改动**：为该假象做过的 visibility 常挂载重构、border 移除实验、(229,229,229) 神秘带逐像素排查等全部回退/失效，最终编辑器回到 1.4.9 原结构 + M1 增量。CoverMakerPage 保留常挂载+visibility 结构（功能等价、已测）。
